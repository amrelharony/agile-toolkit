# Squads audit (2026-05-25)

Scope: `src/lib/squads/{server,validate,invites,colors}.ts`, `src/app/api/squads/{route,[id]/route}.ts`, `supabase/migrations/0010_squads.sql`. Supporting reads of `guest-session.ts`, `require-user.ts`, `redeem/route.ts`, `0011_session_invites.sql`, and `postgrest-js/PostgrestFilterBuilder.ts` for cross-validation.

## Confirmed bugs

### [Low] PATCH `/api/squads/[id]` returns 500 instead of 404 for non-existent / not-owned squad

- File: `src/app/api/squads/[id]/route.ts:80-91`
- What triggers it: An authenticated owner sends `PATCH /api/squads/<some-uuid>` for a squad they don't own (or that doesn't exist). The query `update(...).eq("id", id).eq("owner_id", user.id)...select(...).single()` matches zero rows. PostgREST returns `PGRST116 / no rows` on `.single()`, so `error` is non-null and `data` is null.
- What happens: Route logs the supabase error and returns `{ error: "server_error" }` with HTTP 500. From the client's perspective this looks like a backend crash rather than "not found." It also produces noisy `console.error` logs every time someone (e.g. a stale tab) hits a deleted squad. The DELETE handler on the same file handles the same condition silently with `{ok:true}`, so the two endpoints disagree on the not-found semantics.
- Suggested fix: When the update returns no row, return `{error:"not_found"}` HTTP 404 (after suppressing the PGRST116 log).

### [Low] PATCH ignores empty / whitespace `name` silently when `regenerateCode` is also true

- File: `src/app/api/squads/[id]/route.ts:69-78`
- What triggers it: Owner sends `{ regenerateCode: true, name: "   " }` (or `name: ""`, or `name: "​"` after no sanitization — see next item). The condition `typeof b.name === "string" && b.name.trim()` is falsy for whitespace-only, so `update.name` is NOT set. But `update.code` IS set, so `Object.keys(update).length` is 1 → no `no_changes` error.
- What happens: Caller intended to rename + regenerate; only regeneration happens. Caller has no signal the rename was discarded. UI/CLI consumers will believe their rename succeeded.
- Suggested fix: When `b.name` is present in the body but normalizes to empty, return 400 `invalid_name` regardless of `regenerateCode`. Distinguish "absent" (no field) from "empty/invalid" (present but bad).

### [Low] Squad `name` accepts control / bidi / zero-width characters

- File: `src/app/api/squads/route.ts:79` and `src/app/api/squads/[id]/route.ts:74`
- What triggers it: Owner POSTs `{ name: "Team​" }` or `{ name: "‮Admin" }`. The handler only does `.trim().slice(0, 80)`. The same `sanitizeDisplayName` defense that exists for `display_name` (validate.ts:43) is NOT applied to `name`.
- What happens: The squad name is stored verbatim and (a) returned to guests via `/api/guest/redeem` response (`squadName: squad.name`), (b) likely rendered in the guest UI. A pasted bidi-override survives storage and flips the visual order of subsequent text in the page. Risk is bounded — the owner is the only allowlisted user, so this is owner-self-foot-gun rather than cross-user attack — but the inconsistency with display_name handling is the kind of asymmetry that gets exploited later when a second owner / a sub-admin role is introduced. Flagging as low because the inconsistency is also a maintenance hazard.
- Suggested fix: Run `name` through `sanitizeDisplayName` (or a near-identical helper sized for 1-80 chars) before insert/update.

### [Low] `findActiveSquadByCode` accepts any code length 16-64 even though all minted codes are exactly 32

- File: `src/lib/squads/server.ts:73-94`
- What triggers it: A code that's the right shape but wrong length (e.g. 17 chars) bypasses the early-return and incurs an extra round-trip to Postgres. Not exploitable — the unique-index lookup just returns 0 rows — but it widens the timing oracle slightly (a 16-char unknown code costs a DB hit; a 15-char one returns synchronously).
- What happens: Inconsequential perf/timing leak. The actual security boundary (whether the code is in the DB) is preserved by the unique-index lookup.
- Suggested fix: Make the length check `=== 32` to match the generator. Keep the 16-64 DB constraint as a forward-compat envelope.

### [Low-medium] Redemption endpoint creates duplicate guest profiles with no rate limit

- File: `src/app/api/guest/redeem/route.ts:32-78`, `src/lib/squads/server.ts:101-122`
- What triggers it: A caller holding a valid squad code POSTs `{code, displayName, color}` N times in a row. Each call mints a new `squad_profiles` row with a fresh UUID, a fresh `cookie_secret`, and a fresh httpOnly cookie that replaces the prior one. No idempotency key, no per-IP cap, no per-code cap on `squad_profiles`. The DB has no unique constraint on `(squad_id, display_name)` either, so the duplicates aren't even deduped on the name.
- What happens: (a) A malicious actor with a leaked squad code can pollute the owner's `squad_profiles` table with arbitrarily many rows — each row is small, but uncapped. (b) Each redemption issues a fresh `cookie_secret`, so the prior cookie is silently orphaned (the row still exists with its own secret, but the browser no longer carries it). The orphan profile remains active and shows up in the owner's profile count forever. (c) The display-name collision (next finding) is amplified by the duplication.
- Suggested fix: At minimum, before insert in `createSquadProfile`, check whether a profile with the same `(squad_id, display_name)` already exists in the last N minutes and return its cookie OR reject with a "name taken" 409. Better: rate-limit `/api/guest/redeem` per-IP and per-code. Add a per-squad cap on active profile count.

### [Medium] No display-name uniqueness within a squad — impersonation

- File: `supabase/migrations/0010_squads.sql:64-81`, `src/lib/squads/server.ts:101-122`
- What triggers it: Alice redeems code, picks `displayName: "Alice"`. Bob redeems the same code (or any code under the same squad), picks `displayName: "Alice"`. Both inserts succeed — the DB has no unique constraint on `(squad_id, display_name)`, and there's no application-level check either.
- What happens: Bob is now indistinguishable from Alice in the owner's activity feed, in canvas presence labels, in poker votes, etc. The `color` field disambiguates IF the UI prominently renders the color chip next to every name, but that's a UI invariant the SQL layer doesn't enforce. The full UUID `profile_id` differs but is never rendered. A guest can deliberately impersonate any other guest in their squad whose name they observed.
- Suggested fix: Add a partial unique index: `CREATE UNIQUE INDEX squad_profiles_unique_name_idx ON squad_profiles (squad_id, lower(display_name)) WHERE revoked_at IS NULL;`. Catch `23505` in `createSquadProfile` and surface a 409 `name_taken` to the redeem route.

### [Medium] Owner's `GET /api/squads` and the embedded profile-count query are unbounded

- File: `src/app/api/squads/route.ts:25-50`
- What triggers it: The owner has, over time, accumulated many squads (each kept alive for historic continuity) and many guest profiles. The list query returns ALL squads owned by the user; the follow-up profile-count query does `select("squad_id").in("squad_id", squadIds).is("revoked_at", null)` and then counts in JS by iterating the returned rows.
- What happens: For an owner with, say, 200 squads × 100 active profiles = 20,000 rows pulled into memory just to compute counts. Response size and memory grow linearly. There's no pagination on the squad list and the count query returns one row per profile (not an aggregate). Today the single-owner constraint caps this, but the schema has no such cap, and the count-by-iteration pattern is wasteful even at small scale.
- Suggested fix: Use a `select("squad_id", { count: "exact", head: false })` group-by, or run `select(... profiles:squad_profiles(count))` to push the count into PostgREST. Add `limit/offset` to the squads list, even if it's a generous default like 100.

### [Medium] `listInvitesForGuest` is also unbounded

- File: `src/lib/squads/invites.ts:47-66`
- What triggers it: Same shape as above. As the owner accumulates session invites across many tools/entities, the per-guest listing pulls every active invite into a single response.
- What happens: Same memory / response-size growth. Worse than the squads list because invites are created per-session and may not be revoked promptly.
- Suggested fix: Cap with `.limit(200)` and surface "more available" pagination, OR scope the listing to the most recent N invites by created_at.

## Dismissed / already defended

- **`.or().or()` chaining semantics in `listInvitesForGuest`** (invites.ts:60-63): Confirmed via `node_modules/@supabase/postgrest-js/src/PostgrestFilterBuilder.ts:1947-1951` that each `.or()` calls `searchParams.append("or", ...)`, producing two separate `or=` query params. PostgREST ANDs multiple top-level filters, so the resulting WHERE is `(profile_id IS NULL OR profile_id = X) AND (expires_at IS NULL OR expires_at > now)` — matches intent.
- **`.or()` interpolation injection via `opts.profileId` / `nowIso`**: profileId is sourced from `getGuestSession` which validates UUID format (guest-session.ts:74); nowIso is `new Date().toISOString()` (no untrusted chars). PostgREST tokenizes on `,` and only ISO datetime / UUID chars appear. Safe.
- **`.eq("code", code)` injection in `findActiveSquadByCode`**: PostgrestFilterBuilder uses `searchParams.append`, which percent-encodes the value. Verified at PostgrestFilterBuilder.ts:155. Safe even if `code` contained reserved chars.
- **Squad-code collisions**: 192-bit base64url codes (server.ts:74), unique index enforces uniqueness, collision probability ~1 in 2^96. Effectively zero.
- **`cookie_secret` length**: `randomBytes(32).toString("base64url")` → 43 chars; DB constraint `between 32 and 128` accepts. Verified.
- **Code-regen invalidates old code**: PATCH updates the `code` column in place; subsequent `findActiveSquadByCode(oldCode)` returns 0 rows. Existing guest cookies survive because they bind to `profile_id`, not code. By design.
- **DELETE silent success on non-owned squad**: `eq("id", id).eq("owner_id", user.id)` matches 0 rows, no error, returns `ok:true`. This is the standard "don't reveal whether the row existed" pattern. Intentional.
- **RLS owner-only model**: Policies on `squads` and `squad_profiles` use `(select auth.uid()) = owner_id` for the squads table and an `EXISTS` subselect through `squads.owner_id` for `squad_profiles`. `REVOKE all from anon` plus only-`authenticated` grants means anon clients hit default-deny. Guest mutations go through `/api/guest/*` server routes using service-role (RLS bypass) with explicit cookie validation. The boundary is the route handler — verified consistent with the migration's stated threat model.
- **Defense-in-depth `eq("owner_id", user.id)` in DELETE/PATCH** alongside RLS (route.ts:42, 83): explicitly noted in the source comments as belt-and-braces; correct.
- **CSRF on owner POST/PATCH/DELETE**: Supabase SSR sets auth cookies with `SameSite=Lax`. The state-changing methods POST/PATCH/DELETE don't qualify for the lax-allowed top-level GET navigation, so cross-origin attempts arrive cookie-less and hit the 401 path in `requireAuthorizedUser`. Defended.
- **CSRF on guest endpoints**: Guest cookie set with `sameSite:"lax"` (guest-session.ts:106); same analysis. Defended.
- **HMAC timing attack**: `verifySignature` uses `timingSafeEqual` on equal-length buffers (guest-session.ts:55). Defended.
- **`sanitizeDisplayName` covers the high-impact invisibles**: C0/DEL, soft hyphen, ALM, ZWSP/ZWNJ/ZWJ, LRM/RLM, all the LRE/RLE/PDF/LRO/RLO siblings, the FSI/LRI/RLI/PDI group, line/paragraph separators, BOM. NFC normalize + trim. Enumerated rather than relying on a `\p{Cf}` class — this is the right paranoid-by-default approach. Mongolian Vowel Separator (U+180E) is technically Cf but is non-impactful and not enumerated; not a real bug.
- **Color whitelist**: `isValidColor` is set-membership against an 8-element frozen array (colors.ts:22-28). No injection surface. Color is also char_length-bounded in the DB (4-16 chars).
- **Schema info leak in 500s**: Errors are logged server-side with `console.error` but the response body is a generic `{error:"server_error"}`. No SQL state code, no PG message, no schema names leak to the client. Verified across all three route handlers.
- **Auth/email-verified gate on owner side**: `requireAuthorizedUser` asserts `provider === "google"`, email allowlist, AND email-verified via identities[].identity_data.email_verified OR email_confirmed_at fallback (require-user.ts:78-110). Solid.
- **POST `/api/squads` not idempotent**: Same name → two squads with different codes. By design (names aren't unique, codes are the identity).
- **`revoked_at` columns on squads / squad_profiles**: Never written by any route in this phase. Future-phase plumbing. Not a bug, just dead code on the write side — `findActiveSquadByCode` and `getGuestSession` already read it correctly for forward compat.

## Open questions

- **Cookie revocation strategy.** The current model has no path to invalidate a stolen cookie short of revoking the entire profile row (and no endpoint sets `revoked_at`). A `cookie_secret` rotation would invalidate every prior cookie atomically — should there be a "rotate my key" endpoint, or is the plan to wait for the claim-code phase? Flagging because the comment in 0010_squads.sql:30 says "Compromise of one row's secret only compromises that one profile" — true, but compromise lasts forever-ish.
- **Per-IP / per-code rate limit on `/api/guest/redeem`.** No rate limit visible anywhere in the squad code or in middleware. Is there an infra-level limit (nginx, Vercel edge) the route assumes? If not, the duplicate-profile finding above is straightforwardly exploitable.
- **Squad-revocation UX.** `revoked_at` is checked but not set anywhere. Is the intent that owners only DELETE (hard-delete with cascade)? Soft-revoke would leave history attribution intact while disabling new redemptions / sessions. Worth deciding before phases 2-4 lean on it.
- **`b.name` size cap of 80 chars vs DB constraint of 1-80**: an 81-char input is silently truncated to 80 by `.slice(0, 80)`. Is that intended (forgive long names) or should it 400 (reject so clients learn)?
- **The `count` column in `GET /api/squads` is unused on the front-end?** Worth confirming the front-end actually needs it before optimizing the query — if no, drop the second round-trip entirely.
