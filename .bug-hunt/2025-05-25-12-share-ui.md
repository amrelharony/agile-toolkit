## Confirmed bugs

### [High] Squad invites are silently permanent — no TTL ever sent

- File: `src/components/collab/session-share-modal.tsx:118-129`
- Trigger: any squad invite created via the Phase 2 framework (canvas Phase 3, poker Phase 4).
- What happens: the modal posts `{ squadId, toolId, entityId, role, profileId }` but **never `ttlDays`**, so the API stores `expires_at = NULL` (route line 131-137 leaves `expiresAt` null when no `ttlDays`). The DB allows null (`expires_at timestamptz` with `check (expires_at is null or expires_at > created_at)` — null is fine). Every squad invite ever issued lives until manual revoke.
  - Doubly bad because the `Invite` row already carries an `expiresAt` field in the response (server returns it; type declares it line 40-41) but the UI's active-invites list (lines 247-287) never renders it — so a user who later discovers the field exists can't tell whether each invite has TTL or not.
  - Contrast: canvas's legacy share-link `ShareTab` forces a 1/7/30/90-day dropdown (`share-modal.tsx:343-353`). Same UX expectations don't carry over.
- Suggested fix: add a TTL select to `SessionShareContent` (e.g. "1 day / 7 days / 30 days / never"), include `ttlDays` in the POST body, and render `expiresAt` in the active-invites list with a relative "expires in 3d" or "no expiry".

### [High] Active-invites list shows no expiry info, no copy-link, no squad name

- File: `src/components/collab/session-share-modal.tsx:247-287`
- Trigger: any view of the active-invites list.
- What happens: each row shows only profile-pin + role + revoke button. Missing:
  1. `expiresAt` — even when set, it's silently dropped from render. User can't tell when an invite expires.
  2. Squad name — `Invite.squadId` is in the type but never displayed. If the owner has 3 squads and invites all of them for the same board, the list shows three identical "Anyone in squad — editor" rows with no way to disambiguate.
  3. Copy-link button — no UI affordance to get the guest join URL (e.g. `/guest/canvas/<boardId>` or `/guest/planning-poker/<roomCode>`). The owner has to know the URL shape and construct it manually, or assume the guest already has the squad code.
- Suggested fix: render `expiresAt` with a relative label; hydrate squad name (either annotate in the `/api/sessions` response or look up locally from `squads`); add a copy-link button that builds the canonical `/guest/<toolId>/<entityId>` URL.

### [Medium] `/api/squads` returns revoked squads; modal silently includes them in picker

- File: `src/app/api/squads/route.ts:25-34` + `src/components/collab/session-share-modal.tsx:73-76`
- Trigger: any owner whose squad has been soft-revoked (sets `squads.revoked_at`). Today, the DELETE route does a hard delete (`route.ts:42`), so the field is unused in practice — but the column exists, RLS allows owners to UPDATE it, and any future "soft revoke" flow lands this bug instantly.
- What happens: `GET /api/squads` selects `revoked_at` but does NOT filter `is("revoked_at", null)`. The TypeScript `SquadOption` interface (modal line 19-23) doesn't even include `revokedAt`, so it gets silently dropped from the response payload. The dropdown shows revoked squads as if they were still active. POSTing for one of them succeeds (the POST squad lookup at `sessions/route.ts:141-146` also doesn't filter `revoked_at`) so the invite is created against a revoked squad and is later unreachable by any guest because the squad code has been regenerated.
- Suggested fix: server-side, `GET /api/squads` should add `.is("revoked_at", null)`; defensively, `SessionShareContent` could filter client-side on `(s as { revokedAt?: string }).revokedAt == null`. `POST /api/sessions` should likewise reject revoked squads with 410-Gone.

### [Medium] `SessionShareModal` has no Escape-key handler and no focus trap

- File: `src/components/collab/session-share-modal.tsx:300-331`
- Trigger: opening the bare `SessionShareModal` (currently only planning-poker via `SessionShareButton`). Canvas embeds `SessionShareContent` inside its own carefully built `ShareModal` which DOES have Esc handling (`canvas/components/share-modal.tsx:66-89`) AND `useFocusTrap` (line 130-131).
- What happens: the bare modal only closes via outside-click or the X button. No keyboard-only close, no Tab-key trap (focus escapes to the underlying page), no focus restore to the trigger button on close. WCAG 2.4.3 fail and a regression vs the canvas adopter's handling — the framework is missing what canvas independently re-derived.
- Suggested fix: pull the canvas modal's Esc-handler pattern into `SessionShareModal` directly (window-level keydown that ignores INPUT/TEXTAREA/SELECT/contentEditable targets so the SELECT dropdowns inside `SessionShareContent` collapse-on-Esc without closing the modal). Also wire `useFocusTrap` here.

### [Medium] Modal doesn't surface "existed: true" idempotent-create response

- File: `src/components/collab/session-share-modal.tsx:130-134`
- Trigger: owner re-creates a (squad, tool, entity, profile) tuple that already has an active invite. Server (sessions/route.ts:181-198) handles 23505 by returning 200 with `{ invite, existed: true }`. UI treats that exactly like a fresh create.
- What happens: the owner sees no signal that nothing was created — the active-invites list refresh just shows the row that was already there. Indistinguishable from a successful new create. Confusing if the owner is investigating "why doesn't my invite link work" and clicks "Send invite" again expecting a fresh row.
- Suggested fix: branch on `j.existed === true` from the response and show an inline note ("Invite already active — re-used existing row").

### [Medium] No cancellation guard in `load()`; in-flight requests resolve after unmount

- File: `src/components/collab/session-share-modal.tsx:59-86`
- Trigger: user opens the modal, modal starts `load()`, user closes the modal before the fetch resolves.
- What happens: `setSquads` / `setInvites` / `setLoading` fire on the unmounted component. React 18 swallows the warning silently, but the work is wasted and (more importantly) `selectedSquadId` gets initialized from `sqs[0]?.id` on a closed modal — next time the modal is opened, the initialiser `(prev) => prev || (sqs[0]?.id ?? "")` keeps the prior squad even if the prior modal was for a different entity. Subtle cross-modal state contamination because `SessionShareContent` isn't keyed on the (toolId, entityId) tuple anywhere.
- Suggested fix: add an `abortController`/`cancelled` flag in `load()` and in the per-row revoke/create handlers; reset `selectedSquadId` to "" on unmount (or key the component on `${toolId}:${entityId}` from outside).

### [Low] Revoke button has no per-row pending state

- File: `src/components/collab/session-share-modal.tsx:142-153, 277-284`
- Trigger: user rapid-clicks the trash icon on one invite, or clicks multiple trash icons in succession.
- What happens: `onRevoke` doesn't disable the button or track per-row pending state. Multiple DELETEs fire for the same id; on the server they're idempotent (UPDATE … WHERE id = … sets `revoked_at` once), but if the user clicks two different rows in quick succession the second click can race with the first's setState and produce a flicker where one row appears to come back briefly.
- Suggested fix: track a `Set<string>` of in-flight revoke ids and disable matching buttons.

### [Low] Role default mismatch between adopters

- Files:
  - canvas share-link tab (`src/app/(tools)/canvas/components/share-modal.tsx:250`) — defaults to `"viewer"` (safer default for URL-bearer links posted to channels).
  - Squad invite framework (`src/components/collab/session-share-modal.tsx:56`) — defaults to `"editor"` (squad members are vetted, so editor is the common case).
- This is defensible product design, but the two modals sit side-by-side as tabs in canvas (`share-modal.tsx:152-195`) and the same owner switching between them will routinely create an editor-by-default squad invite right after creating a viewer-by-default link. No build-in confirmation step. Worth flagging because the canvas tabs collapse two mental models into one UI.
- Suggested fix: at minimum, surface the default role in the tab label or button text (e.g. "Send invite (editor)") so the owner can't miss it.

### [Low] Canvas Share button isn't gated on owner mode

- File: `src/app/(tools)/canvas/canvas-client.tsx:735-746`
- Trigger: a viewer/commenter who loads the owner-side `/canvas` route via `?share=<token>&view=readonly` (canvas has a read-only mode it enters when a non-editor share token resolves).
- What happens: the Share button is rendered with no `disabled={mode !== "editor"}` check. A read-only viewer can click it, see the squad tab fail with `squads_401` (since they're not the owner), see legacy share-link creation fail with `ShareTokenAuthRequiredError`. Cosmetically broken; no security impact (the API enforces).
- Suggested fix: `disabled={!activeBoardId || mode !== "editor"}` at line 739.

## Dismissed / already defended

- **Double-submit on POST /api/sessions** — defended. `submitting` flag disables the Create button (`session-share-modal.tsx:233`) for the duration of the request, and the unique partial index on `(squad, tool, entity, coalesce(profile_id, '00…0'::uuid))` returns 200-with-existed for any race that gets past the button-disable. The current implementation has no idempotency key, but the natural-key uniqueness substitutes.
- **Toast on 409** — moot. Neither modal uses any toast helper. `SessionShareContent` has no toast import; canvas's ShareModal uses inline `setCopiedToken` / `setCopyError`.
- **Copy-link missing https:// or roomCode** — N/A for the Phase 2 modal because it never builds or copies a link. The legacy canvas share-link `buildShareUrl` (`share-link.ts:127-141`) correctly uses `window.location.origin` and URL-encodes `boardId`/`token`.
- **Permission check on `/api/sessions`** — defended server-side: `route.ts:141-149` confirms `squads.owner_id = auth.uid()` before insert and returns 404 if not. RLS on `session_invites` further gates.
- **Stale invite ID after revoke** — defended: `setInvites((prev) => prev.filter((i) => i.id !== id))` at `session-share-modal.tsx:149` clears the row from local state on successful DELETE.
- **Esc on canvas share modal with embedded selects** — defended: `share-modal.tsx:66-89` explicitly ignores Esc when the target is INPUT/TEXTAREA/SELECT/contentEditable, so the SELECT dropdowns inside the squad tab collapse-on-Esc without closing the modal. (Planning-poker's bare `SessionShareModal` lacks this entirely — see bug above.)
- **`InviteDialog` (`src/components/shared/invite-dialog.tsx`)** — defined but zero callers. Confirmed dead, not a broken adopter.

## Open questions

1. **Should the Phase 2 framework own copy-link UX?** Today the invite list doesn't show the join URL — the owner is expected to share the squad code separately (via `/settings/squads`) and the guest navigates. But that's a two-step UX. Should the modal also offer "Copy guest URL" that builds `<origin>/guest/<toolId>/<entityId>` and the squad code is already implicit in the cookie? Need product clarity.
2. **What happens to an invite after the host leaves a poker session?** Planning-poker generates a fresh 6-char `roomCode` per host start. The squad invite is keyed on `entity_id = roomCode`, but after `handleLeave` the roomCode is dropped from client state and never recovered. The DB row lives until natural expiry (currently null → forever, see TTL bug). Cleanup hook on session-end is probably warranted, but it cuts both ways — what if the host re-joins under the same code? Currently they can't, because re-entry mints a new code.
3. **Should the canvas share-link tab and squad tab share a single role selector?** They're independent today; the same modal asks "what role for this URL?" and "what role for this squad?" as two separate questions. Could collapse into one if the data model unified, but the threat models differ (URL bearer vs cookie-bound profile) and migration 0011 explicitly keeps the tables separate. Worth confirming this is final.
4. **Should `SessionShareButton` itself be role-gated?** Owner-only is currently by-route (poker host vs guest client), but if a future tool reuses the same client for both owner and viewer modes, the framework offers no guidance. A `disabled={!isOwner}` prop or a hook (`useIsSessionOwner()`) would be safer than each adopter rediscovering the gate.
